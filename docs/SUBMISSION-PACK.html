1. Purpose and scope

IRO provides a proposed, structured route for students and local residents to report non-emergency campus and community issues, receive a reference, and follow safe status updates. A coordinator would review, categorize, route, and update reports. Public information must not expose a reporter or sensitive details.

The submitted interface is a small front-end prototype. It demonstrates issue entry, validation, anonymity by default, a local reference, and a filterable issue board. It does not transmit reports, authenticate users, or provide a monitored complaint or emergency service.

2. Component interaction

Reporter selects a group, category, broad area, and urgency, then describes the issue → IRO validates and returns a reference → this prototype saves only in the browser → a future secure server routes the case to a coordinator → the coordinator publishes a safe status update.

The initial issue cards and sample survey responses are fictional. Do not enter real or urgent incident information into the prototype.

4. Quality, data, and limitations

4.1 Non-functional requirements

AreaRequirement
PrivacyCollect the minimum information needed; anonymous by default; keep private notes and contact details out of public views.
SecurityProduction case details require authenticated role access, HTTPS, protected storage/backups, and audit records. The local demo is not secure storage.
SafetyState that IRO is not an emergency service. Add only a verified urgent contact route before production.
Usability/accessibilityPlain language, visible labels, keyboard access, readable contrast, assistive-technology status feedback, and reduced-motion support.
Responsive designSupport common mobile and desktop widths without horizontal page scrolling.
PerformanceProposed public-page render target: under 3 seconds at the 95th percentile on broadband; measure after hosting.
Integrity/maintenanceProduction status changes are timestamped; categories and routing rules are controlled and documented.
AvailabilityProduction support hours and uptime target must be agreed with the responsible university/community organization.

4.2 Core data objects

IssueReport: reference, group, category, broad area, title, description, urgency, status, created time, anonymity. StatusUpdate: report reference, status, public message, time, coordinator. Coordinator: account and role. SurveyResponse: pseudonymous response ID, group, broad area, and answers. Keep optional contact information separate and restricted in any production system.

4.3 Constraints

The demo uses HTML, CSS, JavaScript, and browser local storage. It has no server, authentication, notifications, file uploads, moderation, case assignment, or real status service. Browser storage may be visible to other users of the same browser profile. Production needs approved routing owners, privacy/retention rules, access control, secure storage, and a staffed response process.

5.2 Ishikawa summary

Effect investigated: fragmented, delayed, and unsafe reporting, with low trust and weak follow-up. Possible causes are people (awareness/ownership/fear), process (separate channels/no references), technology (accessibility/connectivity), governance and trust (unclear privacy/response owner), communication (no updates), and resources/environment (staff, funds, distance, infrastructure). Validate these hypotheses with genuine feedback.
